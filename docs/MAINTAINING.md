# Maintaining adk-tools

Maintainer guide for the `adk-tools` distribution image. Read this
before bumping a tool, adding a new one, or cutting a release.

If you only want to *use* the image, read the top-level `README.md` instead.

---

## 1. Mental model

`adk-tools` is **not** a codebase; it is a **version lockfile plus a build
recipe**. The tools live in their own repositories and are pinned here as git
submodules under `tools/`. One commit of this repo pins one exact combination
of every tool, and the image built from that commit is that combination,
compiled and pre-wired.

The invariant that keeps this trustworthy:

> **One commit of this repo = one combination that passed the verify gate.**

`build.sh` always builds the `verify` stage first (regenerates the demo
headless, runs every tool's test suite and `adk-smoke` inside the image). A
combination that does not pass verify never produces a tagged image. Do not
weaken this: `--skip-verify` is for local iteration only, never for a commit
that lands on `main`.

Everything else (Dockerfile, `bin/` wrappers, scripts, docs) is glue owned by
this repo, licensed GPL-3.0-or-later unless a file's own SPDX line says
otherwise: the files that say Apache-2.0 are Apache-2.0. The bundled tools keep
their own licenses; see `NOTICE.md`.

---

## 2. Branching model

| Branch      | Role                                                                 |
|-------------|----------------------------------------------------------------------|
| `main`      | **Stable.** Every commit is release-quality and passed verify. Release tags (`vYYYY.MM`) live here. |
| `dev`       | **Integration.** Where submodule bumps and new tools land first and get verified. Promoted to `main` at a release. |
| `feature/*` | Short-lived work branches, cut from `dev`, merged back into `dev`.    |

Rules:

- **Never commit tool bumps or new tools directly to `main`.** They go to
  `dev` (or a `feature/*` off `dev`), get built with the verify gate, and reach
  `main` only through a `dev -> main` promotion at release time.
- `main` moves only at releases (and for genuine hotfixes, which are then
  merged back into `dev`).

## 3. Bumping an existing tool

The common case: a tool released a new version and you want it in the image.

```bash
git switch dev

# Option A: follow the tool's branch of the same name as this one
# (.gitmodules declares `branch = .`: on dev each tool's dev, on main its main)
git submodule update --remote tools/<name>

# Option B: pin an exact ref (a tag or reviewed commit)
cd tools/<name> && git fetch && git checkout <ref> && cd ../..

# Rebuild through the verify gate. A broken combo does NOT tag an image.
./build.sh

# Commit the gitlink move. Match the existing message convention:
git commit -am "Bump <name> pin to <ref> (<one-line summary>)"
```

Notes:
- The `describe` and `ref` fields in the baked `manifest.json` update
  automatically from the submodule state; you do not edit `manifest.json` by
  hand (it is generated by `build.sh` and gitignored).
- Keep each bump in its own commit so a regression bisects cleanly.
- Bump only to a commit that exists on the tool's branch of the same name as
  the one you are on (on `dev`, the tool's `dev`), so a later `--remote` bump
  stays on the intended line of development.
- `branch = .` follows the branch you are on, so on a bump branch of your own
  (say `bump/adk`) the tools have no branch of that name and `--remote` fails.
  Point this clone at `dev` for the time of the bump, without touching the
  tracked file, and drop the override afterwards:
  ```bash
  git config submodule.<name>.branch dev     # this clone only, overrides .gitmodules
  git submodule update --remote tools/<name>
  git config --unset submodule.<name>.branch
  ```
- On a tag checkout (`git checkout v2026.11.3`) HEAD is on no branch, so
  `--remote` refuses ("the superproject is not on any branch") instead of
  drifting. `git submodule update --init` gives the release's pins there.
- Regenerate the pin set after staging the bump, and commit it with the
  gitlink: `git add tools/<name> && python3 -B ci/pin_set.py`. The pin set takes
  each tool's commit from the gitlink git has staged, not from the submodule's
  checkout. The image is labelled with the committed pin set, and `build.sh`
  refuses a `ci/pin-set.json` that differs from the commit or from what the
  staged pins give.

### Trying a branch of one tool

```bash
# an arbitrary branch of one tool against the rest of the pinned stack
cd tools/chiplet-studio && git fetch && git checkout feature/x && cd ../..
./build.sh
```

Nothing is staged here: the image carries `feature/x` while its
`org.ihp.adk-tools.pin-set` label still names the pinned commit, so do not run
such an image under an examples checkout's `release-lock.json`.

To develop a Python tool against the pinned stack, mount your checkout over
the baked-in copy:

```bash
docker run --rm -it -v "$PWD/chiplet_kicad_plugin":/opt/adk-tools/chiplet_kicad_plugin ... adk-tools:dev
```

### One-time cleanups of an old clone

After `README.md`'s "Updating an existing clone", depending on how old the
clone is:

- Clones from before the demo moved into `examples/` still carry the
  removed `kicad_designs` submodule as leftovers:
  `rm -rf tools/kicad_designs .git/modules/tools/kicad_designs`
- If the default job count changed since your last build (it keys the
  compile layers), the heavy stages rebuild once (~40 min), then cache
  normally again.
- A `/work/example` from an older image stays as it is. It was the demo copied
  from this clone; the examples now come from adk-examples.

## 4. Adding a new tool

A new tool is a new submodule plus its wiring into the image. Do all of this on
`dev`.

### 4.1 Register the submodule

```bash
git switch dev
git submodule add https://github.com/IHP-GmbH/<Repo>.git tools/<name>
git config -f .gitmodules submodule.tools/<name>.branch .
git add .gitmodules
```

This appends a section to `.gitmodules` and stages the gitlink. The `branch`
line is written afterwards because `git submodule add -b .` refuses the
relative form.

- **Use the HTTPS URL, always.** An SSH (`git@github.com:`) URL breaks anonymous
  `git clone --recurse-submodules`, and `build.sh` copies the URL into the baked
  `manifest.json`, so a wrong one ships inside the image. Maintainers who push
  over SSH rewrite it locally instead of editing the tracked file:
  `git config --global url."git@github.com:".insteadOf https://github.com/`.
- Declare `branch = .`, git's relative form: the submodule follows its branch
  of the same name as the one this repository is on, so one `.gitmodules` is
  right on `dev` and on `main` and a release changes nothing in it. It needs a
  tool with a `main` and a `dev`. A tool whose branches are named otherwise
  keeps an explicit line and an entry in `EXPLICIT_BRANCH` in
  `ci/contracts.py`; the `gitmodules-track` contract fails any other named
  branch, and any missing one.
- A tool whose repository is not published yet cannot be added here: the URL
  would not resolve for anyone else and `NOTICE.md` would cite a dead link. Keep
  that work on a local branch until the repository exists.

### 4.2 Bake it into the image (`Dockerfile`)

The Dockerfile has two parts, split by its `#### thin layer:` line. Above it is
the tools image: what this repository does not write (apt packages, KiCad, PDK
slices, Nix closures, the venv's third-party packages). Below it is our code, in
the `runtime` stage, on that image. `build.sh` rebuilds the tools image only
when `ci/tools_key.py` gives a new key for the part above the line, so put a
tool on the side it changes with.

- **Our Python / data tool** (a submodule of this repository) -- copy the tree
  next to its siblings under `/opt/adk-tools`, below the line (see the
  `COPY tools/...` block, around
  `COPY tools/gds_to_kicad /opt/adk-tools/gds_to_kicad`):

  ```dockerfile
  COPY tools/<name> /opt/adk-tools/<name>
  ```

  A Python package it needs from PyPI goes into the tools stage's venv RUN,
  pinned with a `<NAME>_PIP` ARG; below the line pip installs with no index,
  and `ci/check_thin_layer.py` refuses anything that downloads there.

- **Compiled third-party tool** -- add a dedicated builder stage above the line
  (mirror `kicad-builder`), then copy only the install artifacts into `tools`:

  ```dockerfile
  FROM deps AS <name>-builder
  ARG JOBS
  COPY tools/<name> /src/<name>
  RUN <configure/build/install into /install>
  ...
  # in the tools stage:
  COPY --from=<name>-builder /install/ /opt/adk-tools/<name>/
  ```

  A compiled tool of ours builds below the line, `FROM ${TOOLS_IMAGE}`, the way
  `studio-builder` does. Two heavy builders in the same part run at the same
  time; keep the total compile jobs `<= JOBS`, or the RAM budget goes.

### 4.3 Discovery root (optional)

If the tool expects an env var pointing at its own tree, add it to the `ENV`
block in the `tools` stage (the one with `ADK_ROOT`, `GDS_TO_KICAD_ROOT`, ...). Name it
after the repository, matching the existing convention.

### 4.4 Launcher

Add an executable wrapper `bin/<command>` (the whole `bin/` dir is copied to
`/usr/local/bin` and `chmod +x`). Follow the existing one-liner pattern:

```sh
#!/bin/sh
# <one-line description> (<GUI|CLI>)
exec /opt/adk-tools/venv/bin/python3 /opt/adk-tools/<name>/<entrypoint>.py "$@"
```

For a compiled GUI that needs the in-tree KLayout libs, export
`LD_LIBRARY_PATH` first (see `bin/chiplet-studio`).

### 4.5 Python dependencies

If the tool needs packages in the worker venv, add a pinned `ARG <PKG>_PIP=...`
and a line to the `pip install` in the venv block. **Pin exact versions** -- the
comment there explains why (an unpinned dep can silently flip a verify suite on
a cache-cold rebuild). Bump a pin in its own deliberate commit.

### 4.6 Verify coverage

If the tool ships tests, add a numbered step to the `verify` stage so a bad
bump fails the build. Follow the existing pattern (run under the worker venv,
`QT_QPA_PLATFORM=offscreen` for anything touching Qt).

### 4.7 Docs & notices (mandatory, not optional)

- `NOTICE.md` -- add the component to the right table with its **SPDX license**
  and **source URL**. If it is GPL, also add it to the corresponding-source
  obligation paragraph. Verify the license from the tool's own `LICENSE` /
  source headers; do not guess (`-only` vs `-or-later` matters).
- `README.md` -- add the command to the Tools table; mention any new data root.

### 4.8 Build, verify, commit

```bash
./build.sh              # verify gate must pass
git add .gitmodules tools/<name> Dockerfile bin/<command> NOTICE.md README.md
git commit -m "Add <name> tool (<summary>)"
```

`manifest.json` needs no manual edit; `build.sh` regenerates it from the
submodule set.

## 5. Removing a tool

Removing a submodule cleanly is easy to get wrong: a leftover gitdir under
`.git/modules` survives the removal and comes back on the next `add`.

```bash
git switch dev
git submodule deinit -f tools/<name>
git rm tools/<name>
rm -rf .git/modules/tools/<name>        # <-- the step people forget
```

Then remove every wiring point added in section 4: the `COPY`/builder stage,
the `ENV` root, `bin/<command>`, the venv pins, the verify step, and the
`NOTICE.md` / `README.md` entries. Finally `./build.sh` and commit.

## 6. Cutting a release

Calendar versioning: `vYYYY.MM` (e.g. `v2026.07`), and `vYYYY.MM.N` for a point
release of it (e.g. `v2026.11.2`). Continues the scheme started at `v2026.06`.

The order and every check are in `RELEASE_CHECKLIST.md`; follow it. The
mechanics behind its steps:

1. Get `dev` green: `./build.sh` passes on the tip of `dev`.
2. Promote to `main`:
   ```bash
   git switch main && git merge --ff-only dev   # or a reviewed merge commit
   ```
3. Nothing to change on the track. `.gitmodules` and `ci/integration-refs.json`
   declare every branch as `.`, so on `main` a `--remote` follows each tool's
   `main` and on `dev` its `dev`, from the same bytes; the release changes the
   pins only. One tool moves on its own: KiCad-ADK-MOD releases separately, so
   its `main` can be ahead of the pin, and on `main` a `--remote` takes
   `tools/kicad` to that newer release.
4. Tag locally first, so the image built next names the release: an
   **annotated** tag on `main` (signed if a GPG key is set up):
   ```bash
   git tag -a vYYYY.MM -m "adk-tools vYYYY.MM: <headline>"
   ```
5. Build the tagged commit from a fresh clone of this checkout
   (`git clone --recurse-submodules <this checkout>`, which carries the tag; a
   clone of `origin` has neither the promoted `main` nor the tag) and confirm
   the baked manifest is clean. The build needs the sibling checkouts
   `staging.pin` lists (`STAGE_SIBLINGS`, by default the clone's parent
   directory) and the die records (`STAGE_DIE_VIEWS_DIR`):
   ```bash
   ./stage-sources.sh --check && ./stage-die-views.sh --check
   ./build.sh                                    # tags adk-tools:dev locally
   docker run --rm adk-tools:dev cat /opt/adk-tools/manifest.json
   ```
   `meta` must read `vYYYY.MM`, every tool URL must be an `https://github.com/`
   one, and no filesystem path may appear. If anything is wrong, delete the
   local tag, fix, and start again from step 1. Then run the license check
   of the staged trees (`RELEASE_CHECKLIST.md`, "The tag") on this build's
   `staging/`. Only once it passes, take this image as the release's reference
   image: the adk-examples release lock names its ID
   (`docker image inspect --format '{{.Id}}' adk-tools:dev`).
6. Push:
   ```bash
   git push origin main
   git push origin vYYYY.MM
   ```
7. Merge any post-release fixes back into `dev`.

**The image is not public.** People who run a release can build its image
themselves, and `run.sh` holds their build to the examples' release lock by its
pin set (`docs/RUN_SH.md`). Building the image needs the sibling checkouts
`staging.pin` lists and the die records (the `die-views/` folder of
adk-examples), so a clone of this repository alone does not build. A release's
image can also be handed to a named person in two private forms, each only after
the image the release was proven on is built and its checks are green:

- an archive, written by `save-image.sh <image ID> <directory>`, with its sha256
  and size, and a copy loaded from it and run by `run.sh` against the release
  lock before it is handed over;
- the private package `ghcr.io/ihp-gmbh/adk-tools`, pushed by
  `release.sh vYYYY.MM[.N] <image ID>` once the release is on `main`. It pushes
  the version tag only, never `latest`, and stops (exit 3) unless the package
  reads private before and after the push and an anonymous read of the tag is
  refused. The package takes its access from the ADK-Tools repository's roles
  through the image's `org.opencontainers.image.source` label; anyone else gets
  access on the package, by hand. `release.sh` never changes a visibility and
  never deletes a version.

Each hand-over and each access grant is decided for that person and that
release. Do not add a "pull the image" or "download the image" instruction to
the docs while the image is not public.

### Version identifiers must agree

Three identifiers name the same release; keep them consistent:

| Identifier      | Where                          | Set by                                    |
|-----------------|--------------------------------|-------------------------------------------|
| git tag         | `vYYYY.MM` on `main`           | `git tag -a` (step 4)                     |
| manifest `meta` | baked in the image, shown by `adk-tools` | `build.sh` via `git describe --tags` |
| image tag       | `ghcr.io/ihp-gmbh/adk-tools:vYYYY.MM[.N]`, private, when the image is pushed | `release.sh vYYYY.MM[.N] <image ID>` |

`build.sh` derives `meta` from `git describe --tags`, so an image built from
the tagged commit reports `vYYYY.MM`; one built before the tag, or a few
commits later, reports another release's name with `-<n>-g<sha>`. That is why
the tag comes before the build.

## 7. Reproducibility notes

- Submodule pins are the lockfile: a fresh `git clone --recurse-submodules` at
  a given commit reproduces the exact tool set.
- Non-submodule pins that also gate reproducibility live as `ARG`s in the
  `Dockerfile`: `UBUNTU_IMAGE`, `KICAD_LIBS_TAG`, `SG13G2_REF`,
  `PYCELL_API_REF`, `PYPREPROCESSOR_REF`, `KLAYOUT_PIP` and the other `*_PIP`
  versions. Bump these deliberately, in their own commit, and re-verify.
- The base image is pinned by digest (`UBUNTU_IMAGE`, an `ubuntu:24.04`
  manifest index). Every apt package comes from the Ubuntu snapshot at
  `APT_SNAPSHOT`, and `docker/apt.lock` and `docker/pip.lock` hold what the
  tools image installed. The runtime's first step diffs them against the tools
  image's own copies and stops on any difference. When a change moves the tools
  key and the new tools image holds other packages, copy its locks out
  (`docker run --rm --network none --entrypoint cat adk-tools:tools-<key12>
  /opt/adk-tools/tools/apt.lock > docker/apt.lock`, the same for `pip.lock`)
  and commit them with the change. The build still depends on live github.com +
  gitlab.com egress. For strict byte-level
  reproducibility see the known limits in `RELEASE_CHECKLIST.md`.
